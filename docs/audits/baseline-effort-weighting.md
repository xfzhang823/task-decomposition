## Executive summary

`relative_effort_weight` is generated by the operational-decomposition LLM.
The prompt intends it to be a ratio estimate of each subtask's share of
baseline human working time. Python does not estimate the value. After provider
validation, Python normalizes the raw values by their sum to a synthetic
`W0 = 1.0`, and optionally applies the same ratios to a caller-supplied
measured baseline effort.

An arbitrary overall numeric scale is therefore acceptable: weights of `12`
and `4` express a three-to-one relationship and normalize to the same ratio as
`3` and `1`. The concern is not the arbitrary scale; it is whether the
proportions are supported by explicit assumptions about human working time.

The implementation has no formal baseline-effort calibration scale, reference
subtask, uncertainty range, or structured assumption record. The prompt now
requires a concise `effort_rationale` describing frequency and
effort-per-occurrence assumptions, while still avoiding required absolute
units, benchmark retrieval, or citations. Naming O*NET or other benchmark
sources in the prompt does not establish that the provider retrieved or used
them.

## Scope and end-to-end flow

The notebook constructs a task-only request in
[`notebooks/task_decomposition_end_to_end.ipynb`](../../notebooks/task_decomposition_end_to_end.ipynb):

1. `build_task_request()` creates a `TaskDecompositionRequest` containing a
   `TaskReference` with `task_name` and `task_description`, plus
   `task_context={"domain": ...}` (notebook cell source around lines 217-218).
2. `execute_task()` calls `decompose_task(build_task_request(inputs), provider)`
   (around lines 223-224).
3. `decompose_task()` calls the provider's operational-decomposition stage,
   validates the untrusted response, performs semantic evaluation/repair, and
   then calls `_allocate_baseline()`:
   [`application/task_decomposition.py`](../../src/task_decomposition/application/task_decomposition.py).
4. `_allocate_baseline()` reads each provider-generated
   `relative_effort_weight`, normalizes the weights through
   `domain.allocate_effort()`, and creates `BaselineEffortAllocation` rows.
5. The notebook's task table displays the raw
   `OperationalSubtask.relative_effort_weight`, not the normalized
   `BaselineEffortAllocation.weight_ratio`.

The notebook path supplies no `baseline_effort`, so it exercises normalized
shares only. `TaskDecompositionRequest.baseline_effort` is optional and is not
included in the provider payload by `stage_payload()`.

## Observed implementation

### Request construction

The request contract contains `task`, `task_context`, optional
`baseline_effort`, request metadata, and provenance; it contains no weighting
rubric, reference activity, frequency model, or estimation assumptions:

[`contracts/provider.py`](../../src/task_decomposition/contracts/provider.py:26-35)

`stage_payload()` sends the provider only the task and task context for this
stage:

[`providers/_shared.py`](../../src/task_decomposition/providers/_shared.py:55-64)

Consequently, a measured parent effort may be available to the application but
is not an input from which the LLM derives the relative values.

### Shared prompt template

All three provider adapters import the same
`OPERATIONAL_DECOMPOSITION_PROMPT`:

- [`providers/openai.py`](../../src/task_decomposition/providers/openai.py:351-364)
- [`providers/gemini.py`](../../src/task_decomposition/providers/gemini.py:165-173)
- [`providers/deepseek.py`](../../src/task_decomposition/providers/deepseek.py:166-174)

The exact relevant prompt text is:

> Assign each subtask a positive `relative_effort_weight` representing its estimated share of baseline human effort.

> Estimate expected effort as typical occurrences per parent task × relative human effort per occurrence.

> Use a consistent parent-task workload basis; do not double-count volume or assume conditional activities occur every time.

> Provide a concise rationale for each subtask's relative_effort_weight.

The repair template adds:

> Ensure every subtask has a positive, unnormalized `relative_effort_weight` (no hours or percentages).

It also requires a concise `effort_rationale` and preserves valid existing
weights and rationales during repair.

The same prompt also asks for concise names and descriptions, stable IDs, and
valid dependencies. It says to use empty dependency and provenance arrays
unless needed and to omit unnecessary metadata. It explicitly asks for an
`effort_rationale` for each subtask's weight.

### Parsing and validation

`parse_model_payload()` converts JSON text where necessary and validates it
against the stage schema:

[`providers/_shared.py`](../../src/task_decomposition/providers/_shared.py:118-137)

`OperationalSubtask.relative_effort_weight` is a positive `Decimal` when
present, or null, and `effort_rationale` is a required non-empty string:

[`contracts/stages.py`](../../src/task_decomposition/contracts/stages.py:29-40)

Structural validation enforces:

- unique subtask IDs;
- contiguous one-based sequence indexes;
- valid dependency references and dependency ordering;

and effort-per-occurrence fields. The semantic evaluator assesses rationale
transparency and directional plausibility instead of requiring absolute
measurements or source citations.

work at a usable granularity and whether effort assumptions are transparent and
directionally consistent with the relative weights:

[`evaluation/rubric.py`](../../src/task_decomposition/evaluation/rubric.py:5-28)

### Normalization and optional absolute allocation

`_allocate_baseline()` treats provider weights as the sole allocation source:

[`application/task_decomposition.py`](../../src/task_decomposition/application/task_decomposition.py:249-282)

It creates a synthetic parent effort of one unit with `PER_OPERATION` basis,
then calls `allocate_effort()`:

[`domain/allocation.py`](../../src/task_decomposition/domain/allocation.py:12-45)

The arithmetic is effectively:

```text
weight_ratio_i = raw_weight_i / sum(raw_weights)
```

If `baseline_effort` is supplied, the same raw weights are applied to that
parent effort. No alternative weights, equal-effort fallback, or authoritative
LLM accounting total is introduced.

The raw provider values remain on the operational subtasks. The normalized
values are stored separately as `BaselineEffortAllocation.weight_ratio`; the
absolute values are optional.

## Interpretation of the current semantics

The prompt's intended meaning is a ratio estimate of aggregate active human
working-time share per parent-task execution. Thus, weights `12` and `4` mean
the first subtask is estimated at three times the baseline human working time
of the second. The overall numeric scale is arbitrary because normalization
removes it.

That interpretation is only partially formalized. The field itself is
dimensionless and has no unit or time basis. The implementation does not
distinguish active work from elapsed waiting time, complexity, difficulty,
cost, or staffing capacity. Duration, frequency, and workload volume are
mentioned in the prompt, but no structured occurrence or volume model exists.

The current source does not define whether the estimate should represent an
average case, typical case, or a workload mix including exceptions. The task
description may contain such information, but the model is not required to
state which assumptions it used.

There is no baseline reference subtask or calibration anchor. The reference-
class estimation instructions elsewhere in the repository apply to added
AI-interaction and AI-verification work, not baseline
`relative_effort_weight` values.

current allocation source and `allocate_effort()` as the deterministic
normalization authority:

[`docs/audits/task-effort-separation.md`](task-effort-separation.md:56-123)

Two documentation limitations remain:

1. The root README describes semantic quality as including “effort
   plausibility” ([`README.md`](../../README.md:220-224)), but the current
   semantic rubric does not explicitly validate effort plausibility or
   recalculate weights.
2. The end-to-end audit requirements distinguish baseline shares from new AI
   work, but place reference-class estimation nearby. The implementation's
   reference-class estimator is for added work, not baseline weights:
   [`docs/task_decomposition_end_to_end_semantic_audit_requirements.md`](../task_decomposition_end_to_end_semantic_audit_requirements.md:21-27).

The prompt's named benchmark sources should also not be described as evidence
that those sources were consulted. The current source records only an
instruction to use them when available; it does not retrieve or attach them.

## Interpretability gaps

- No formal baseline weighting rubric or calibration scale exists.
- No structured duration, frequency, volume, case-mix, or exception-rate input exists.
- No structured operating assumptions, estimate basis, confidence, or uncertainty are returned; the free-text rationale retains the required core assumptions.
- No reference subtask or external quantitative anchor is required for baseline weights.
- The model does not receive the optional measured parent effort in the notebook path.
- A raw value such as `4` has meaning only relative to the other weights in that response.
- Semantic validation now reviews effort plausibility, rationale transparency, and consistency between stated frequency, effort per occurrence, and relative weights.
- Provider differences can produce different proportions while satisfying the same contract.

Tracing may preserve provider invocation messages, parsed responses, and
validation events when tracing is enabled:

[`tracing.py`](../../src/task_decomposition/tracing.py:293-328)

However, if a historical run did not record a trace artifact, the exact
messages sent to the provider and exact provider response cannot be established
from the current source alone.

## Minimal proposed improvements

The remaining items below are recommendations for future refinement; they are
not required by the current contract.

1. Define the baseline quantity explicitly as aggregate active human effort per
   parent-task execution.
2. State whether duration, occurrence frequency, workload volume, and exception
   mix should be combined into the estimate, and provide a small calibration
   rubric or examples.
3. Decide whether exception work belongs in separate subtasks or in explicit
   frequency/case-mix assumptions.
4. Consider structured estimation metadata only if the free-text rationale
   proves insufficient; the current contract intentionally avoids a second
   rationale object or required absolute measurements.
5. Clarify that baseline weights are ratio estimates and do not require an
   arbitrary universal numeric scale; the validation concern is unsupported
   proportions and hidden assumptions.
6. Refine the existing semantic plausibility criterion with examples if
   repeated provider evaluations show a need for calibration.
7. Clarify in documentation that added-work reference-class estimates are
   separate from baseline `relative_effort_weight`.
8. Preserve exact provider messages and returned weights in trace artifacts
   for historical audits.
