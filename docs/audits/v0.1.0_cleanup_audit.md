# v0.1.0 Cleanup Audit

## Executive summary

This audit found no confirmed dead runtime module or symbol in `src/task_decomposition`. The package uses a `src/` layout, has no console entry-point registration, and its public exports, provider adapters, staged pipeline, allocation/accounting helpers, and benchmark support are exercised by tests or documented application paths.

The clearest cleanup candidates are repository artifacts rather than production code: one empty top-level file, one duplicate notebook, sixteen cached transformation outputs with no repository references, and an NTFS `Zone.Identifier` sidecar. Several verification and semantic-evaluation documents describe earlier repository states and should be corrected or explicitly marked historical before release. The packaging lower bound should also be reviewed because the current PEP 639 metadata requires a modern setuptools backend.

This is an audit only. No files were deleted or modified as part of the audit.

## Public API and dynamic-use assessment

The `src/` package is discovered through setuptools package discovery. No `console_scripts` or other project entry-point registration was found. Provider selection is performed through the application provider factory and optional provider adapters, not through an unsearched plugin directory. The package’s lazy provider imports and import-boundary tests are intentional and should be preserved.

No active source references were found for the removed legacy concepts `transformation_intent`, the legacy `DecompositionRequest`, compatibility-provider symbols, or the former `ports`/old allocation paths. Existing absence tests and historical documents intentionally mention some of those names. They are not cleanup targets in the current package.

The broad root export surface is the main compatibility risk. A symbol having few internal imports is insufficient evidence for removal because consumers can import it directly. Any future consolidation of exports should first check downstream consumers and provide a deliberate deprecation policy.

## Items explicitly to preserve

- `src/task_decomposition` application, contracts, domain accounting/allocation, validation, evaluation, interfaces, and provider adapters.
- Deterministic accounting ownership in `domain/accounting.py` and the staged allocation-to-accounting handoff.
- The four cached replay fixtures used by `benchmarks/replay_transformations.py`.
- `benchmarks/processes.json`, opt-in live benchmark code, and credential-free benchmark tests.
- `tests/test_import_boundary.py`, provider-isolation tests, package smoke tests, and accounting/staged-pipeline regression tests.
- `README.md`, `AGENTS.md`, reference accounting/decomposition documents, and useful historical migration reports.
- `LICENSE`, `.env.example`, and packaging metadata required for the v0.1.0 distribution.

## Recommended cleanup order

1. Correct or label current-facing verification and semantic-evaluation documentation, because stale release claims are the highest user-facing risk.
2. Resolve the setuptools/PEP 639 build lower bound and document the `python -m build` prerequisite.
3. Confirm provenance, then remove the empty file, OS sidecar, and unreferenced cached outputs.
4. Consolidate the duplicate trace notebook after checking external links.
5. Review optional developer tooling and notebook dependencies; retain them if notebook/editor support is part of the contributor workflow.
6. Defer any public-export reduction until downstream consumers and a compatibility policy are established.

## Proposed verification after any cleanup

- Run `pytest` and the repository-required Ruff, format, compile, and `git diff --check` commands.
- Build both wheel and sdist; inspect that only package runtime resources and the license are included.
- Install the wheel in a fresh environment and run the public import/runtime smoke test from outside the repository.
- Run offline replay tests and confirm the four retained cached artifacts remain loadable.
- Search for every removed path/basename with `rg`, including docs, notebooks, tests, and benchmark scripts.
- Check `git ls-files` for secrets, OS sidecars, bytecode, caches, build outputs, and unintended benchmark artifacts.
- If public exports or provider tooling changes, run import-boundary/provider-isolation tests and inspect downstream consumer compatibility.

## Audit conclusion

The release cleanup opportunity is concentrated in stale verification prose and clearly unreferenced repository artifacts, not in confirmed dead production code. The safest v0.1.0 preparation is to update current-facing documentation and packaging metadata, then remove only the low-risk artifacts after provenance confirmation. Historical reports and the public API should remain intact unless a separate compatibility-reviewed change is approved.
